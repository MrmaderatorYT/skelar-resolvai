## 1. Новий пітч (фідбек) — згоден

Фідбек правий у головному:
- refund коштує гроші одразу, а chargeback стається не з кожним незадоволеним клієнтом;
- фраза «інші лише відповідають, а ми діємо» не витримує перевірки, бо Fin і Zendesk уже виконують refund-и (підтвердив і Codex, `.task/CODEX_REVIEW.md` §2).

**Нова формула:**
> Defuse допомагає subscription-командам вирішувати складні billing-звернення: перевіряє платіжний контекст, виконує лише дозволені компанією дії, пропонує утримання тим, кому воно доречне, і передає спірні випадки людині з готовими доказами.

**Чим відрізняємось (глибина, а не слоган):** система знає, який саме платіж оскаржується; де куплена підписка (картка, App Store чи Google Play); чи вже було повернення; чи відкритий dispute; що policy дозволяє; що вже виконано (audit, idempotency). Generic-агент такого контексту не має.

**Сарказм** лишається, але лише як сигнал для пріоритету й тону відповіді. На повернення він не дає права (див. `docs/security.md` і §6 CODEX_REVIEW).

### 4 сценарії з фідбеку вже є в даних

| Сценарій | Тікети | Що показує |
|---|---|---|
| Людина просила скасувати, а звернення пропустили | T20 (`cancel_flow_abandoned: 2`), T35 (третє звернення) | Скасування одразу, наступного небажаного списання не буде, повторного звернення теж |
| Підтверджене подвійне списання | T32, T33 | Повертаємо саме дублікат. Якщо дубліката нема — уточнюємо, а не «вирішуємо» |
| Забув скасувати й просить refund | T10, T13 | Діють правила компанії: вікно повернення, використання, історія повернень → людина |
| Хоче паузу | T34 | Пауза за згодою клієнта |

**Чого бракує:** сценарію утримання, коли знижку чи паузу дають тільки тим, кому вона доречна. Це якраз твоя ідея (§2).

**Кому продаємо:** не всім subscription-компаніям. Наш покупець — команда, яка вже платить за billing-чергу, повторні звернення, помилкові списання та dispute-и. Компаніям, які заробляють на складному скасуванні, ми не потрібні, і це нормально.

**Чесно щодо попиту:** потреба в розв'язанні проблеми є, але потреба саме в нашому продукті не доведена. На хакатоні можна запитати SKELAR-менторів: «де ваша billing/support-команда сьогодні втрачає найбільше часу чи грошей?». Їхню відповідь варто вставити в слайд.

## 2. Retention-профіль + захист від роздачі знижок

### Чому це головне
- **Знімає заперечення «ви зменшуєте нашу виручку».** Defuse не лише чесно скасовує, а й зберігає частину клієнтів, яким доречна пауза чи знижка.
- **Ринок це вже підтверджує** (цифри вендорів, орієнтовні): добре налаштований cancel flow утримує 10–34% тих, хто намагається скасувати (Churnkey — середнє по платформі 34%; Skio — 15–30%).
- **Ризик, який ти правильно побачив:** якщо знижка дістається кожному, хто натиснув «скасувати», клієнти вчаться скасовувати заради знижки, а знижку отримують і ті, хто й так лишився б. Це пряма втрата маржі. Практики радять 20–30% на 2–3 місяці і не давати 50%+, бо це привчає скасовувати заради знижки.

### Закон: одна пропозиція, потім скасування
California AB 2863 (діє з 1.07.2025) дозволяє «save offer», якщо бізнес одночасно повідомляє, що клієнт може завершити скасування будь-коли. Якщо клієнт наполягає — скасовуємо одразу (юристи називають це «one save rule»). Точне формулювання треба звірити зі статтями 17601–17602 Bus. & Prof. Code.

**Правило для policy:** не більше однієї пропозиції за звернення. Якщо клієнт відмовився або повторив «cancel», скасовуємо без нових пропозицій.

### Дані профілю (що додаємо в seed і в Customer 360)

| Поле | Звідки в реальній компанії | Навіщо |
|---|---|---|
| `acquisition_channel` (meta_ads / tiktok / google / organic / referral) + `funnel` (web_quiz / app_store) | Атрибуція: UTM, AppsFlyer/Adjust, web-квіз | Канал впливає на якість клієнта; з web-квізу ми знаємо його ціль |
| `quiz_goal` (sleep / stress / focus) | Відповіді web-квізу | Пропозиція під ціль: «додамо програму для сну» |
| `tenure_months`, `paid_renewals` | Білінг (Stripe / Solidgate / RevenueCat) | Лояльність; новим клієнтам знижку не даємо |
| `engagement_30d` (сесії, streak) | Продуктова аналітика (Amplitude / Mixpanel) | Хто реально користується → пауза доречна; хто ні → чесне скасування |
| `offers_redeemed_12m`, `last_offer_at` | Наша таблиця пропозицій | Головний захист від повторних знижок |
| `refunds_last_180d`, `chargebacks_lifetime` | Білінг | Уже є |
| `identity_cluster` (той самий card fingerprint / email / device на кількох акаунтах) | Stripe card fingerprint, device ID | Захист від мультиакаунтів «нова пошта → нова знижка» |
| `cancel_reason` (дорого / нема часу / не користуюсь / баг / подорож) | Класифікатор (LLM) з тексту тікета | Пропозиція під причину |

### Правила eligibility (детерміновані, у policy, не в LLM)

```
offer_type за причиною:
  too_expensive   → discount 25% × 2 міс  (або downgrade на дешевший план)
  no_time/travel  → pause 1–2 міс
  not_using       → pause 1 міс або чесне скасування
  bug             → fix + extend_access_7d, без знижки

eligible, якщо ВСІ умови виконано:
  - intent = cancel (НЕ refund / dispute / duplicate / injection / account)
  - нема dispute_signal і нема відкритого диспуту  (людині, що погрожує банком, — refund-path, а не торг)
  - tenure_months ≥ 2 і paid_renewals ≥ 1
  - offers_redeemed_12m == 0
  - refunds_last_180d == 0 і chargebacks_lifetime == 0
  - identity_cluster без пропозицій за 12 міс
  - бюджет пропозицій за місяць не вичерпано (наприклад, ≤ 15% cancel-запитів)
  - не в holdout-групі (10% eligible не отримують пропозицію → міряємо реальний ефект)
інакше → чесне скасування одразу

в одному зверненні — лише одна пропозиція; «ні» або повторне «cancel» → скасування
LLM лише визначає cancel_reason; тип пропозиції, глибину знижки й eligibility вирішує код
```

**Метрика для дашборда:** save rate серед eligible проти holdout, утримання через 30 днів після «збереження», вартість знижок і частка отриманих знижок за кластером ідентичності. Без holdout ми не знаємо, скільки знижок пішло тим, хто й так лишився б.

### Відкриті дані
- **KKBox Churn (WSDM Cup 2018, Kaggle)** — справжні дані підписочного музичного сервісу: `members` (`registered_via`, місто, вік), `transactions` (`payment_method_id`, план, `is_auto_renew`, `is_cancel`, дата закінчення), `user_logs` (активність). Близько 21.5 млн транзакцій. Мітка churn: нема продовження протягом 30 днів після закінчення підписки. **Використання:** після хакатону на них можна довести, що канал реєстрації, автопродовження й активність передбачають churn, тобто на чому будувати eligibility. На хакатоні не імпортуємо: це гігабайти і немає тексту тікетів.
- **IBM Telco Customer Churn** — tenure, тип контракту, спосіб оплати. Маленький, підходить як приклад.
- **Висновок для сьогодні:** розширюємо синтетичний seed (поля з таблиці вище) і чесно пишемо на слайді «schema mirrors KKBox/real billing; values synthetic».

### Нові тікети в eval (щоб фіча була виміряна)

| Тікет | Профіль | Очікувано |
|---|---|---|
| «Too expensive for me right now, cancel please» | 7 міс, 0 пропозицій, активний | Одна пропозиція: −25% на 2 міс + кнопка «cancel anyway» |
| Той самий текст | 3-тя знижка за рік / той самий card fingerprint, що й у 2 інших акаунтів | Скасування одразу, без пропозиції |
| «I'm travelling, cancel» | 1 тиждень з нами | Скасування одразу (tenure < 2) |
| «Cancel or I'll dispute it» | будь-який | Без торгу: refund-path і policy |

## 3. Плагінна система / YAML

### Що в ідеї сильне
- **Бізнес-аргумент:** «кожна компанія підключає свою policy і свої дані без програмістів». Це відповідь на «послідовне застосування власної policy» з фідбеку і на питання про інтеграції.
- **Технічний аргумент:** конектори через інтерфейси — те, що SKELAR оцінює як «архітектуру».

### Чому повна версія — пастка
- **Динамічні плагіни.** У Go пакет `plugin` працює лише на Linux/macOS, крихкий до версій і не працює на Windows. У Java знадобиться classloader або ServiceLoader. За 4 години це не стабілізувати.
- **Firebase, Postgres і JDBC одразу.** Firebase — це service account, SDK і модель документів. Три конектори означають три точки відмови на демо. «jsdc» — мабуть, JDBC; це лише Java-річ (у Go — `database/sql` + драйвер).
- **Редагування правил через UI (ListView) чіпає гроші.** Хто завгодно в UI міняє ліміт auto-refund. Потрібні валідація, approval, версіонування й audit — це ще одна фіча.
- **Секрети.** Ключі БД, вписані прямо в YAML, рано чи пізно потраплять у git.

### Що робимо (мінімальна версія, ~1 год)

```yaml
# defuse.yaml — policy та джерела даних компанії
policy:
  refund:
    full_max_days: 14
    full_max_sessions: 2
    partial_max_days: 30
    partial_share: 0.5
    auto_limit_usd: 60
    doc: docs/policy/refunds.md
  retention:
    max_offers_per_ticket: 1
    min_tenure_months: 2
    cooldown_months: 12
    monthly_budget_share: 0.15
    holdout_share: 0.10
    offers:
      too_expensive: { type: discount, percent: 25, months: 2 }
      no_time:       { type: pause, months: 2 }
    doc: docs/policy/retention.md
  risk:
    weights: { dispute: 0.40, sarcasm: 0.25, aggression: 0.20, money: 0.15, per_contact: 0.10 }
    bands: { high: 0.5, medium: 0.3 }

datasources:
  customers: { type: json, path: data/customers.json }        # реалізовано
  billing:   { type: json, path: data/payments.json }         # реалізовано
  # customers: { type: postgres, dsn: ${DATABASE_URL} }       # той самий інтерфейс; секрет лише з env
  # analytics: { type: firebase, project: ${FIREBASE_PROJECT}, credentials: ${GOOGLE_APPLICATION_CREDENTIALS} }
```

1. **Policy читає пороги з YAML, а не з констант.** Значення, з якими проходять усі 38 тестів, лишаємо дефолтними. Під час завантаження валідуємо: межі 0..1, ліміт > 0, невідомі ключі — помилка старту.
2. **Інтерфейси конекторів:** `CustomerSource`, `BillingProvider`, `TicketSource`, реєстр за полем `type`. Реалізуємо тільки `json` (те, що вже є). `postgres` — якщо лишиться час: 1 таблиця, лише читання. Firebase не робимо.
3. **UI «Policy»:** список правил лише для читання; кожне правило з `doc:` відкриває .md (`docs/policy/*.md`) з поясненням «чому так». Це і є ListView, прив'язаний до .md, тільки без небезпечного редагування.
4. **Секрети лише через `${ENV}`.** Під час старту сервер відмовляється запускатись, якщо в YAML лежить буквальний DSN із паролем.
5. **На слайді:** «Policy-as-config + connector interfaces: компанія підключає свої правила й дані. Демо — JSON-конектор; Postgres і Firebase — той самий інтерфейс».

## 4. Переписування на Go

### Факти
- **SKELAR справді використовує Go:** вакансії портфельних компаній — Go + PostgreSQL + GraphQL + Kubernetes/GCP; payment-backend на PHP/Go. Але в них є й PHP та інші стеки, тож «SKELAR на Go» — правда лише частково.
- **Критерії оцінки мову не називають.** Technical Execution — це архітектура, якість коду, безпека й тести.
- **«Go швидший» тут не важить.** Один тікет — це 1–3 с на LLM-виклик, а policy в будь-якій мові працює за мікросекунди. Реальні плюси Go: один бінарник, швидкий старт і білд, простий деплой.
- **Java-версія готова:** 61 тест, усі 38 рішень збігаються з еталоном, перевірена разом з UI. Go на цьому Mac ще не встановлений (`brew install go` — 1 хв). Офіційний Anthropic Go SDK існує (`anthropic-sdk-go`).

### Ціна переписування
- Третя версія бекенду за день (Python → Java → Go).
- Порт ядра (store, policy, executor, pipeline, API з тим самим JSON-контрактом, тест на 38 кейсів) я зроблю приблизно за 1–1.5 год. Плюс час Діми, щоб розібратися в коді.
- Ці 1.5 години не підуть на retention-фічу та YAML, а саме вони сильніше піднімають бізнес-цінність, на якій ми зараз слабкі.

### Рекомендація
- **Діма пише на Go помітно швидше, ніж на Java** → переходимо на Go. Але лише з умовою: той самий API, щоб фронт не мінявся; тест на 38 gold-кейсів — гейт; freeze о 14:30.
- **Інакше лишаємо Java**, а «SKELAR використовує Go» закриваємо однією фразою в Q&A: «ядро — 600 рядків детермінованої policy, портується за годину; ось тест на 38 кейсів, який це гарантує».
